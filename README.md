# Bright Smile Dental: front-desk chatbot

> Full README (architecture, design decisions, evals, prioritization) comes in the final step. This
> covers running and deploying it.

## Run locally

```bash
cp .env.example .env        # add ANTHROPIC_API_KEY and/or GEMINI_API_KEY (either alone works)
uv sync
make dev                    # http://localhost:8000 (chat) and /staff (alerts)
make test                   # unit tests
make eval                   # scenario evals against the real LLM (see evals/)
```

Locally the app uses SQLite (`dental.db`). It creates tables and seeds demo data on first start.

## Deploy: Render (web) + Supabase (Postgres)

Render's free filesystem is wiped on every restart, so all state lives in Supabase. The app won't
start on Render with a SQLite `DATABASE_URL`.

### 1. Supabase

1. Create a project at supabase.com (free tier). Save the database password.
2. **Connect** (top bar) → **Connection string** → choose the **Transaction pooler**, which is
   port **6543**. Copy the URI and put your password into it:
   `postgresql://postgres.<project-ref>:<password>@aws-0-<region>.pooler.supabase.com:6543/postgres`
3. That URI is `DATABASE_URL`. No manual SQL is needed.

How the app uses it (`app/db.py`, `make_engine`):
- **`NullPool`.** The transaction pooler already pools server connections and hands each
  transaction to any of them, so the app keeps no client-side pool of its own.
- **`prepare_threshold=None`.** psycopg's prepared statements are disabled, because they can't
  survive moving between pooled server connections.
- **`sslmode=require`.** It's added automatically for any non-local host.
- **Startup:** creates missing tables (`create_all`), then runs the idempotent seed. The seed fills
  empty tables and adds slots up to 4 weeks out, and never drops or overwrites anything, so restarts
  are safe.

  `create_all` only *creates* tables. A schema change to an existing table needs a migration tool
  (Alembic), which is listed under next steps.

Check double-booking protection against the real database before going live. The script runs in a
throwaway schema and drops only that schema, so production tables are untouched:

```bash
uv run python scripts/contention_check.py "<DATABASE_URL>" 10
```

### 2. Render

`render.yaml` is a Blueprint:

| Setting | Value |
|---|---|
| Build | `pip install uv && uv sync --locked --no-dev` |
| Start | `.venv/bin/uvicorn app.main:app --host 0.0.0.0 --port $PORT --proxy-headers --forwarded-allow-ips='*'` |
| Health check | `/health` (also a good URL for an uptime pinger) |

`--proxy-headers --forwarded-allow-ips='*'` makes uvicorn take the client IP from Render's
`X-Forwarded-For` header, so the per-IP rate limit (20 POSTs per minute) sees patients' real IPs
rather than Render's proxy.

Environment variables (`render.yaml` declares them all):

| Key | Value |
|---|---|
| `ANTHROPIC_API_KEY` | secret (prompted) |
| `ANTHROPIC_MODEL` | `claude-haiku-5-5` |
| `GEMINI_API_KEY` | secret (prompted) |
| `GEMINI_MODEL` | `gemini-3.5-flash-lite` |
| `LLM_CHAIN` | `claude,gemini` |
| `DATABASE_URL` | Supabase transaction pooler URI (prompted) |
| `STAFF_TOKEN` | generated by Render; paste it on `/staff` |
| `DAILY_LLM_BUDGET_USD` | `3` |
| `OFFICE_TZ` | `America/Los_Angeles` |

The free plan spins down after idle time; the first request then takes ~30-60s while it wakes.
